Lexy — AWS live-test setup checklist

Prepared 10 October 2026 · For the AWS administrator and Lexy application administrator

Scope: enable signed email-delivery callbacks and secure private résumé tagging. Preserve existing models, provider routing, commercial tiers and native hiring. Offers remain human-approved and human-operated. This document does not authorize a send, rotate a key, change AWS policies, publish the app or prove live delivery.

Item Observed status

2. Email callbacks — application administrator

  1. Establish the published HTTPS API URL for the environment that owns the test offer and database records. This may be a controlled pilot publication, not a market launch. Do not register a workspace .replit.dev URL as the permanent AWS destination. If an existing API is hosted elsewhere, verify that its current code, configuration and records match the intended environment.
  2. The application route is POST /api/webhooks/ses-events. The endpoint template is <PUBLISHED_API_BASE_URL>/api/webhooks/ses-events; this is a placeholder, not a configured URL.
  3. Move INBOUND_EMAIL_SECRET into the project's secure Secrets storage, coordinating removal of the duplicate ordinary variable and application restart/republication. Preserve the existing value if existing signed outreach links must remain valid. Any rotation must be coordinated with integrations using this secret and affected signed links; never paste it into chat, tickets or this document.
  4. Set SES_SNS_TOPIC_ARNS to the exact permitted topic ARN, or a comma-separated list of exact ARNs. No wildcard. Topic ARNs are configuration metadata, not credentials.
  5. Keep SES_CONFIGURATION_SET, the SES sender and the existing region unchanged. Apply the required settings to the actual published API environment, not only development. The webhook captures its settings at startup.
  6. The application requires the shared secret on every request, including SNS subscription confirmation. Prefer a trusted HTTPS relay that adds X-Webhook-Secret to requests forwarded to Lexy. Direct SNS can use the supported ?secret=<SECRET> transport, but full URLs then contain a credential: restrict access and ensure URL/query logging is redacted throughout the transport. Never circulate the populated URL.
  7. If the publication is private/password-protected, ordinary SNS requests cannot simply sign in. Use a properly configured external-access mechanism or trusted relay. Replit's production external access token and Lexy's webhook secret are different credentials; one does not replace the other. A relay can supply both the platform authorization and application header without exposing credentials in URLs.
  8. Do not enable ALLOW_UNSIGNED_SES_EVENTS, remove SNS signature validation or weaken the topic allowlist to make a test pass.

3. Email callbacks — AWS administrator

  1. In the existing SES region, identify the configuration set named by the current SES_CONFIGURATION_SET. Add or verify an enabled SNS event destination using a Standard topic, not FIFO.
  2. Enable Send, Delivery, DeliveryDelay, Bounce, Complaint, Reject and Rendering Failure events. Open/click tracking is not required. Keep other existing event destinations intact.
  3. Merge the following statement into the topic's access policy, substituting the actual account, topic ARN and configuration-set ARN locally. Do not replace unrelated existing policy statements. 
{
  "Sid": "AllowExactSesConfigurationSet",
  "Effect": "Allow",
  "Principal": { "Service": "ses.amazonaws.com" },
  "Action": "sns:Publish",
  "Resource": "arn:aws:sns:<REGION>:<ACCOUNT_ID>:<TOPIC_NAME>",
  "Condition": {
    "StringEquals": {
      "AWS:SourceAccount": "<ACCOUNT_ID>",
      "AWS:SourceArn": "arn:aws:ses:<REGION>:<ACCOUNT_ID>:configuration-set/<CONFIGURATION_SET_NAME>"
    }
  }
}
  1. For an encrypted topic, verify the chosen KMS configuration also permits the required SES/SNS publishing path. Do not resolve this by granting broad wildcard access or exposing the topic publicly.
  2. Create an HTTPS subscription to the reachable endpoint or approved relay. Keep SNS's signed JSON envelope intact; disable Raw message delivery if that option is exposed. Lexy accepts SNS's default text/plain JSON and application/json.
  3. Verify the subscription is Confirmed in AWS, not PendingConfirmation. A webhook's HTTP acknowledgment alone is not proof AWS completed the subscription. Inspect SNS delivery diagnostics if it remains pending.

4. Private résumé storage — AWS administrator

  1. Identify the IAM user/role actually used by Lexy's S3 client through its current AWS credentials. Do not modify an unrelated SES identity or request a new access key merely for this permission fix.
  2. Resolve the current bucket and private prefix from the administrator's secure configuration. Confirm the actual résumé object keys before applying the resource scope. Do not post credential values in chat.
  3. Add the following narrowly scoped permission statement to that principal's existing policy. Preserve its existing object read/write permissions. 
{
  "Version": "2012-10-17",
  "Statement": [{
    "Sid": "LexyPrivateResumeTagging",
    "Effect": "Allow",
    "Action": [
      "s3:GetObjectTagging",
      "s3:PutObjectTagging"
    ],
    "Resource": "arn:aws:s3:::<CONFIGURED_BUCKET>/<CONFIGURED_PRIVATE_PREFIX>/resumes/*"
  }]
}
  1. If AccessDenied persists, inspect explicit bucket-policy denies, permission boundaries and organization SCPs. A new Allow cannot override an explicit Deny. Also retain any existing KMS permissions if the bucket uses SSE-KMS.
  2. Keep S3 Block Public Access enabled. Do not grant s3:*, make résumés public, add broad ACL permissions, bypass tag-based ownership checks or alter old candidate bindings.

5. Evidence required before marking the checks passed

Email callback check

  • Obtain explicit human authorization for one fresh synthetic offer delivered to an approved, controlled real test inbox. Do not resend an old offer or fabricate historic delivery tags.
  • Record the original SES message ID, exact offer version and send attempt; confirm AWS emits a signed, allowlisted callback matching them and the intended recipient.
  • Verify Lexy changes from provider acceptance to the actual delivery/failure state. “SES accepted,” “subscription confirmed,” and “mail arrived” are distinct facts.
  • Verify callback processing does not change offer approval, terms, candidate acceptance, employment or fees. Duplicate callbacks must not duplicate effects. Use only isolated test records for any failure/retry exercise.

Private résumé check

  • Under the same application IAM principal, prove GetObjectTagging and PutObjectTagging succeed for a disposable object in the scoped résumé namespace.
  • Use fictional PDF and DOCX documents to verify new upload, ownership tagging, candidate attachment and permitted reads.
  • Prove unauthenticated, foreign-tenant and unauthorized staff reads fail; erased/replaced/hidden documents stay inaccessible. Use disposable fixtures rather than modifying old Linx work orders or documents.
  • Remove the exact owned test records and objects afterward. Retain request IDs and outcomes, not credentials, signed URLs or private résumé content.

The machine-to-machine résumé importer has a separate LEXY_IMPORT_API_KEY requirement; that is not necessary to fix normal authenticated résumé uploads and is not part of this two-item checklist.

6. What the tech team should report back

  • Published API URL and its visibility/access arrangement — without credentials or secret query parameters.
  • Configuration-set name, enabled event types, approved SNS topic ARN and Confirmed subscription status.
  • Confirmation that the webhook secret is securely stored and applied to the correct environment — not its value.
  • Confirmation that the actual S3 principal has the two scoped tagging permissions, plus a successful disposable-object probe and request IDs.

After these are supplied, the live checks still need to run. Administrator configuration confirmation is not itself a completed end-to-end test.
