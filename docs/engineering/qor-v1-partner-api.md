# QOR interview partner API v1

The [OpenAPI 3.1 contract](../../lib/api-spec/openapi.yaml) defines the two `qor-partner` operations (`submitQorInterviewRequest` and `getQorInterviewRequest`), their strict input, statuses, and response examples. The server prefix is `/api`. No webhooks are registered.

## Partner integration

1. **Submit** `POST /api/partner/v1/interview-requests` with the approved brief, recruiter-selected candidate, and selection reference. Require `Authorization: Bearer` and `Idempotency-Key`. Keep the same key for the lifetime of this submission, including when retrying after a timeout or rotating the credential. `201` records a request; `200` returns the same receipt for the same normalized payload and key. Changing the payload or resubmitting the same external application under a different key returns `409`. Intake does not create a local job, profile, or interview, and does not send anything.
2. **Poll** `GET /api/partner/v1/interview-requests/{requestId}` using the response `Location` or the returned UUID. Start at 15 seconds, back off on repeated failures or inactive requests, and read again before presenting report content. Responses are `private, no-store`. A miss, other employer, or inaccessible candidate returns the same `404`.

| Status field | Values |
|---|---|
| `invitation.status` | `not_sent`, `ready_to_share`, `staff_reported_sent` |
| `interview.status` | `awaiting_review`, `prepared`, `in_progress`, `completed`, `expired`, `abandoned`, `needs_attention` |
| `reportStatus` | `not_ready`, `processing`, `awaiting_review`, `approved`, `withdrawn`, `needs_attention` |

`staff_reported_sent` is a manual attestation, not mailbox delivery. `processing` means the session completed and the summary isn't present yet; a recorded terminal summary failure is `needs_attention`. Report `awaiting_review` can include a summary that still needs generation and approval as a structured evaluation. After approval, a changed source or withdrawal makes the report unavailable. L3XY cannot recall any copy already taken outside the service.

### Exact employer credentials

- Apply `lib/db/drizzle/0116_qor_interview_requests.sql` through the approved database migration flow, before provisioning QOR. It uses private PostgreSQL tables with forced RLS and no browser-role access. Do not schema-push over the existing security SQL.
- For each employer and environment, provision a separate high-entropy credential with the literal format `qor_` followed by 43 base64url characters (32 randomly generated bytes, without padding). Generate and share it through the approved secret manager. Store **only the lowercase SHA-256 hex digest of the entire credential** in `qor_partner_credentials.digest`, along with `tenant_id`, `can_create`, `can_read`, and `expires_at`. `can_create` and `can_read` authorize `interviews:create` and `interviews:read`, respectively. Roles and credentials are not set via request JSON. No real credential is provided or installed here.
- Set `revoked_at` to invalidate a credential. A rotated credential for the exact same employer retains that employer's request IDs and idempotency history. A credential cannot inherit parent/child tenant access.
- QOR is a backend integration; do not use the generated client hooks to put the credential in browser code. Neither the legacy résumé-import key nor a staff session credential is accepted on these partner routes.

## L3XY reviewer workflow

Use the existing work-order, candidate, plan and Evaluation screens for their normal creation and approval. The **staff support API**, not the QOR credential, ties them to the partner request. It uses an active L3XY session for a `tenant_admin` of the exact employer. It is available at:

`GET|POST /api/partner-review/v1/interview-requests/{requestId}`

1. **Review intake.** A GET returns the QOR employer brief, selection reference, external candidate reference, and current status. QOR shares the request UUID with the reviewer. Intake does not store the submitted name or email in plaintext; the reviewer uses the candidate profile in QOR and the existing L3XY candidate screen for any needed reviewed intake. Only an employer-local, contact-eligible candidate whose current email matches the submitted normalized address can be linked.
2. **Prepare.** The local open, approved work order must match the submitted title and description; set its client work-order number to the QOR external job ID. Add `?jobId=…&candidateId=…&planId=…` to the staff GET, review the displayed plan, then POST:
   ```json
   {
     "action": "prepare",
     "jobId": "fixture-work-order",
     "candidateId": "fixture-candidate",
     "planId": "fixture-plan",
     "reviewHash": "<current preparation.reviewHash>",
     "confirm": true
   }
   ```
   The native session uses a frozen copy of the plan. Preparation sends no invitation. A previously bound request cannot mint a replacement; a known native interview for that candidate and work order blocks parallel preparation.
3. **Share separately.** Get the latest `invitation` review. POST `{"action":"release_invitation","reviewHash":"<current invitation.reviewHash>","confirm":true}` to obtain the native room URL and verified recipient for manual sharing. After sharing, POST the same review hash with `action: "record_invitation_sent"`. Neither action sends mail. The candidate room still uses the native verification, consent, and interview runtime; the room URL never appears in QOR polling.
4. **Review evidence.** After the interview and summary are ready, generate and human-approve the native structured evaluation. Then GET the staff review and inspect `reportReview.report`. If it is absent, the native evaluation isn't yet eligible (for example a draft, stale review overlay, or an evaluation associated with a different session). Separately POST:
   ```json
   {
     "action": "approve_report",
     "reviewHash": "<current reportReview.reviewHash>",
     "expectedVersion": 0,
     "confirm": true
   }
   ```
   Use `reportReview.expectedVersion` from the fresh GET, not the example value. Approval binds the exact projection, native evaluation revision and QOR session. The returned report contains only summary, competency evidence and limitations; it excludes draft content, raw answers, recordings, private notes, identity verification, and hiring decisions. Review the exact projection for any sensitive material before approving.
5. **Withdraw if needed.** POST `{"action":"withdraw_report","expectedVersion":1,"confirm":true}` using the latest `expectedVersion`. A prior review cannot silently reauthorize withdrawn content. A changed native evaluation also invalidates prior QOR approval. Publishing or withdrawing a report does not advance, reject, make an offer, or alter a hiring stage.

## Isolated verification

From the repository root:

```sh
pnpm --filter @workspace/api-server run test:qor-sandbox
```

The sandbox starts its own socket-only PostgreSQL instance, applies the actual QOR SQL, and runs two local HTTP listeners with two synthetic employers. It blocks outbound HTTP and does not inherit provider credentials. Native completion and assessment rows are synthetic fixtures, not a live AI interview. The tests exercise scope separation (including identical external IDs), eight concurrent submissions, zero sessions on intake, concurrent frozen-plan preparation, separate invitation and interview states, exact QOR disclosure and withdrawal, and credential revocation and candidate erasure. It does not certify a production migration or live provider delivery.

**Result:** All eight scenarios passed (nine reported passes including the parent test), including health, authenticated polling, and malformed JSON against the full Express API. The API build, type-check, and repository build guards passed. No live messages or provider requests were made, and the migration was applied only to the temporary sandbox database.
